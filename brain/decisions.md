# Decisions

- 2026-10-11 — Clean-room build; TMOG is closed-source commercial (C++/Win32, paid Pro tier), so no decompiled code or licence logic is reused. Why: copying it is infringement and the native pseudocode isn't rebuildable anyway.
- 2026-10-11 — Go with an embedded web UI in an Edge/Chrome `--app` window. Why: builds with plain `go build` (no cgo/GUI toolkit), easiest to customize, still a single exe.
- 2026-10-11 — Windows data via ntdll/PDH/SCM/registry directly, only `golang.org/x/sys` as a dependency. Why: no gopsutil bloat, full control over fields, matches the "build the metrics core" step.
- 2026-10-11 — Loopback API guarded by per-launch token cookie, Host/Origin checks, JSON-only POST. Why: the API can end processes; an open local server would be exploitable from any web page.
- 2026-10-11 — Separate Edge profile for elevated runs. Why: a Chromium profile must not be shared across integrity levels.
- 2026-10-11 — Replaced the browser/localhost UI with a native Win32 UI built on tailscale/walk. Why: user wants a real Windows application, not a local web server; Walk gives native controls from pure Go with no cgo.
- 2026-10-11 — Collapsed tree rows show subtree totals; parent PID only trusted if parent started before child. Why: busy branches stay visible when folded, and Windows reuses PIDs so a dead parent's PID can mislead.
- 2026-10-11 — Windows resources (manifest/icon) generated with go-winres into a .syso; empty Walk toolbar hidden. Why: Walk needs Common-Controls v6, and its toolbar window otherwise paints over the tab strip.
- 2026-10-11 — Redesign: dark owner-drawn shell (sidebar, cards, 3x supersampled graphs) with native dark list views. Why: user found the classic-controls UI ugly and wanted TMOG as inspiration; owner-drawn back-buffered painting is also what removes the refresh blink.
- 2026-10-11 — Drive health via IOCTL_STORAGE_QUERY_PROPERTY with access 0 (no admin, no vendor driver). Why: gives model, temperature and the NVMe SMART log natively; CPU package power / die temps are NOT available this way and are shown as unavailable rather than faked.
- 2026-10-11 — Walk layout quirk: items with the largest minimum size are sized first and only get a proportional share of spare space, so page bodies use stretch factor 1000 (bodyStretch). Why: header/footer shares were otherwise wasted and the page was centred instead of filling.
- 2026-10-11 — All drawing code works in 96-DPI design units scaled by gs inside the primitives. Why: Walk scales fonts by DPI but raw pixel layout did not, clipping text at 150%.
- 2026-10-11 — Flight recorder keeps samples in memory only by default; on-disk history is opt-in. Why: samples contain process names.
- 2026-10-11 — TMOG analysis stayed at the declared-interface level (imports, resources, shipped data files, public notices). No code read, nothing about its licensing or Pro gating. Why: user asked for inspiration only, and its licence forbids bypassing Pro access controls.
- 2026-10-12 — Ryzen power via the Windows Energy Meter counters (RAPL_Package0_PKG / _CoreN_CORE, mW). Why: native, no driver, matches Ryzen Master within a few watts.
- 2026-10-12 — Ryzen temperature is an optional external source (LibreHardwareMonitor web server on loopback), not an in-process driver. Why: reading Tctl needs ring-0 PCI/SMN access; gotm will not ship or install a kernel driver itself. The alternative is AMD's Monitoring SDK using the Ryzen Master driver already running here (needs the SDK from AMD's portal).
- 2026-10-12 — Downloaded LibreHardwareMonitor v0.9.6 to third_party/ (SHA-256 verified against GitHub's published digest), NOT executed: the exe is unsigned and it needs the separate PawnIO driver for CPU sensors. Why: installing a kernel driver and running elevated is the user's call (anti-cheat in Battle.net/EA/Epic is installed).
- 2026-10-12 — Installed "RyzenMasterSDK 1.2.3.5" and C:\Program Files\AMD\RyzenMaster\bin are runtime only (Device.dll, Platform.dll, CPUMetricsServer.exe, AMDRyzenMasterDriver.sys): no headers, docs or sample. Why: the interface lives in the SDK header, which AMD distributes only via its portal and its licence forbids redistribution (the community .NET wrapper says so too). gotm will not guess the DLL's C++ vtable layout: a wrong call goes to a kernel-driver-backed SMU interface.
- 2026-10-12 — Waiting on the user for one of: (A) AMDRyzenMasterMonitoringSDK.exe 3.1.1.5478 from AMD's Technical Information Portal (SHA-256 8ACD2D2F557CBBC041FC3E9B5B83DD0E39E919133FBD69AB5B4956177A43007C), or (B) PawnIO + LibreHardwareMonitor (already downloaded to third_party/, not run).
- 2026-10-12 — Used the AMD Monitoring SDK via its documented C++ vtable order, not guesses: headers came from AMD's SDK package the user supplied. The SDK's ICPUEx is getter-only, and device 0 is validated (type == CPU, non-empty name, plausible temperature) before any read. Why: a wrong slot could otherwise hit a kernel-driver-backed call; with the monitoring DLL nothing can write CPU settings.
- 2026-10-12 — The SDK DLL directory comes only from HKLM (`...\RyzenMasterMonitoringSDK\InstallationPath`) and must pass WinVerifyTrust; there is no config/env override. Why: config.json is user-writable, and gotm loads the DLL elevated, so a per-user path would be a privilege-escalation route.
- 2026-10-12 — SDK use is opt-in (Settings), off by default, with a crash marker (`ryzensdk.pending`). Why: Device.dll registers a kernel-driver service and a native fault can't be recovered from Go; the marker prevents a crash loop.
- 2026-10-12 — Did not use Ryzen Master's own Platform.dll 3.0.2 (it exports Set* overclocking calls and a larger ICPU interface). Why: its vtable differs from the documented monitoring one, and a wrong index could call a setter.
- 2026-10-12 — REA could not be used for deeper analysis of Device.dll (no Ghidra/IDA provider configured); relied on the documented headers and runtime validation instead.
- 2026-10-12 — Effective clock = Processor Frequency x per-core % Processor Performance / 100. Why: the frequency counter is the nominal clock on this Ryzen; the performance counter exceeds 100 while boosting (measured 116% = ~4.9 GHz). It is Windows' smoothed estimate; the AMD SDK gives truer effective clocks when enabled.
- 2026-10-12 — Per-process GPU memory uses the "Local Usage" counter, not "Dedicated Usage". Why: Dedicated Usage summed to 73 GB on a 16 GB card (virtual allocations); Local Usage matches Task Manager scale. The adapter total still comes from Dedicated Usage (matches nvidia-smi: 7123 MiB).
- 2026-10-12 — AMD iGPU clock/power/temperature left as "Not exposed". Why: no Windows API; AMD ADL needs its SDK headers and I will not guess struct layouts.
- 2026-10-12 — Dark context menus and header text use uxtheme ordinals 133/135/136 (AllowDarkModeForWindow, SetPreferredAppMode, FlushMenuThemes), looked up at runtime on build ≥ 18362 and skipped if absent. Why: no documented API exists; this is what Explorer/Notepad++ rely on, and failure just leaves the light look.
- 2026-10-12 — Header text colour comes from a window-procedure hook installed above Walk's list-view procedure (SetWindowLongPtr), not SetWindowSubclass. Why: Walk forwards header NM_CUSTOMDRAW to the header's own procedure, so a comctl32 subclass below Walk never sees it (verified by logging).
- 2026-10-12 — Shortcuts go through a per-window pre-translate handler. Why: Walk's ShortcutActions only run when the focused HWND is a Walk window, which the native list views inside tables are not (Ctrl+F/Ctrl+4 did nothing in testing).
- 2026-10-12 — Screenshots for verification use PrintWindow (window content only), never screen copies. Why: a screen copy picked up part of an unrelated window; it was deleted.
- 2026-10-24 — Own Go installer (tools/setup) instead of Inno Setup. Why: no third-party tool to install on the build PC, fully testable in `go test`, and it installs for all users into Program Files so an elevated gotm never runs from a user-writable folder.
- 2026-10-24 — Process actions take a Target (PID + creation time) and act on the verified handle; critical Windows processes are refused (BreakOnTermination or core name from System32). Why: PID reuse made End task / End tree hit unrelated processes; malware using a core name elsewhere must stay killable.
- 2026-10-24 — Uninstall never goes through cmd.exe; HKCU entries are refused while elevated; %VARS% use system values only. Why: each path let a standard user's program run code as administrator.
- 2026-10-24 — The AMD SDK switch and crash marker live in HKLM\SOFTWARE\gotm; elevated writes to %APPDATA%\gotm refuse junctions/links (internal/safepath). Why: user-writable state must not steer an elevated process.
- 2026-10-24 — Tests never touch the real settings folder (config.OpenAt). Why: a test overwrote the user's config.json during this review.
- 2026-10-24 — Screen-reader support is a real UI Automation provider written as raw COM vtables (uia.go), not MSAA annotations. Why: only a provider can expose the items painted inside one HWND as separate, invokable elements with focus events; Walk's Dynamic Annotation names a whole window only.
- 2026-10-24 — UIA calls are marshalled to the UI thread (ProviderOptions_UseComThreading; Run() calls CoInitializeEx STA). Why: provider code reads paint-time item lists without locks and can click items directly.
- 2026-10-24 — AMD sensors through ADL (atiadlxx.dll) rather than ADLX. Why: plain C exports that the shipped driver already carries, no SDK headers to bind beyond the public enum; ADLX is COM-style vtables with a larger surface.
- 2026-10-24 — High contrast = system colours mapped onto the same palette struct, with resource hues pushed away from the background. Why: one `T` read at paint time means every page follows without per-page code; HC users keep their own text/selection colours.
- 2026-10-24 — Elevated behaviour is tested by a throw-away Windows service built from the test binary (runs as SYSTEM) and removed afterwards. Why: the only honest way to prove service control and ending a SYSTEM-owned process without touching the user's real services.
- 2026-10-24 — Trusted Signing via signtool + Microsoft's dlib fetched from NuGet and Authenticode-verified, not the PSGallery module. Why: the module pulls three NuGet packages through PackageManagement and a dotnet tool; the direct path is one Microsoft-signed DLL the build verifies itself, and the same signtool verify gate covers both signing modes.
